# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Streamlit web app that turns rare-earth-element (REE) solvent-extraction research papers (PDFs) into a queryable SQLite database. One writer uploads PDFs; an LLM extraction pipeline produces one row-per-data-point table against a fixed **35-column schema** (the lab's 26 spreadsheet columns, then 9 appended in 2026-11); after automatic QA and human review, rows from **openly-licensed papers only** merge into a master DB that two read-only consumers (a calculator and an AI assistant) sit on top of.

Two design documents, referenced by section number throughout the code:

- `plan.md` is the original pre-implementation design plan — authoritative on *intent*. Code comments saying `README §6` etc. refer to **plan.md's** sections (the plan used to live in README.md; README.md is now a public-facing overview with no section numbers). The code has moved past the plan in places (e.g. the pinned prompt is now `extraction_v16`, not `extraction_v5.1`). Trust the code for current behavior; use the plan for rationale.
- `docs/curve_extractor_plan.md` is the deterministic curve extractor's design doc — comments saying `plan §4.2` etc. refer to *its* sections.

## Commands

```bash
# Run the app (multi-page: home = extraction, pages/ = DB / Calculator / Assistant / Analysis)
streamlit run app.py

# Tests (pure/offline — no API calls, no network)
python -m pytest                    # full suite (~500 tests; 3 need the Swain & Otu PDF in data/incoming/)
python -m pytest tests/test_solve.py            # one file
python -m pytest tests/test_checks.py -k monotonicity   # one test by name

# Headless bulk runs over the open-access manifest (Batches API; never writes the DB)
python -m extraction.bulk submit --first-batch [--dry-run]   # or --tier A [--tier B] --limit N
python -m extraction.bulk status                             # reconcile with the API, show jobs + review queue
python -m extraction.bulk collect                            # stage every ended batch (resumes, never re-pays)

# Hosted read-only viewer (Database + Analysis pages over a DB snapshot; no API key)
streamlit run viewer.py                                      # locally, after `python -m database.snapshot`
./publish_viewer.sh                                          # HEAD + a fresh snapshot -> the PRIVATE hosting repo Streamlit Cloud deploys

# Compare this pipeline with the sibling ree-extraction-local pipeline, per paper (offline, read-only)
python -m evaluation.compare path/to/papers/ --local-runs ../ree-extraction-local/data/runs [--ref-dir refs/]
```

There is no lint/format config and no `pytest.ini` — `conftest.py` just puts the repo root on `sys.path`. Dependencies: `pip install -r requirements.txt` (a `.venv/` already exists).

## Environment

Config is read once in `config.py` from `.env` at the repo root. Keys: `ANTHROPIC_API_KEY` (required for extraction/assistant, not for tests), `REQUIRE_PASSWORD`/`WRITE_PASSWORD` (write gate), `EXTRACTION_PROMPT_VERSION` (default `extraction_v16`), `EXTRACTION_MODEL` (default `claude-sonnet-5-5` since 2026-10-06 — same price as `claude-sonnet-5`, which every measurement in this file was taken on; supports everything this pipeline sends: code execution, Files API, task budgets (the docs list Sonnet 5 as *not* supporting them), 1h cache TTL, batches, and the 2576px high-resolution vision tier that figure digitization depends on. Its breaking changes vs Sonnet 5 don't touch this pipeline as long as it keeps adaptive thinking, never forces `tool_choice`, sends no `temperature`/`top_p`, and keeps continuations append-only — a replayed Sonnet 5.5 thinking block after any edit to the system prompt, tools or earlier messages is a 400, so `_transcript` must only ever append), `ASSISTANT_MODEL` (`claude-haiku-4-5-...`), `EXTRACTION_EFFORT` (empty by default = API default `high`; `output_config.effort`, the lever after loop length since thinking is ~3/4 of output tokens — Sonnet 5.5 recalibrated effort levels and suggests `medium` for multistep tool use, so A/B on Swain before changing it), `EXTRACTION_TASK_BUDGET_TOKENS` (default `500000` — a self-moderated backstop on total tokens per extraction call, not a hard cap; keep it generous, a too-tight budget makes the model silently under-digitize a multi-element paper instead of erroring). `LOCAL_PIPELINE_RUNS_DIR` (optional: the sibling ree-extraction-local project's `data/runs`, the default for `evaluation.compare --local-runs`). `OPEN_ACCESS_MANIFEST` (optional; default `data/open_access/manifest.csv`, curated by another agent — never write to `data/open_access/`) and `OPEN_LICENSES` (optional comma list; default cc0, public-domain and every CC variant — `config.OPEN_LICENSES`). Never hardcode paths or model IDs — add them to `config.py`.

## Architecture: three pillars over one DB

The master SQLite DB (`data/master.db`) is the hub. **Pillar A is the only writer; Pillars B and C are strictly read-only** and query through the `v_current_best` view, never the raw `extractions` table.

- **Pillar A — extraction** (`app.py` home page, `ingestion/`, `extraction/`, `validation/`, `database/`): upload → dedup → LLM extract → QA → human review → merge.
- **Pillar B — calculator** (`pages/2_Calculator.py`, `calculator/`): deterministic ppm↔mM / molar-ratio / concentration math, cross-checked against DB typical ranges.
- **Pillar C — assistant** (`pages/3_Lab_Assistant.py`, `assistant/`): Anthropic tool-calling agent that answers questions by querying the DB and calling the calculator — never by inventing numbers.
- **Analysis** (`pages/4_Analysis.py` UI only, over the pure `analysis/` package; read-only like B and C): curves, pH½ across the series, separation factors, slope analysis and a cross-paper overlay, as Altair charts with a CSV of the plotted data each.

### Analysis page (`analysis/`)

- A curve is one paper's rows for one element, `Figure/Table` and set of fixed conditions along the varied x: `paper_id` + `validation/curves.py`'s `curve_key(x)` — the one curve definition QA shares — which is the element plus *every* condition column (descriptors such as `Sources`, `Material Process`, `mixing method` included) except x and what moves with x (pH for an acid-concentration x; the per-element feeds for a total-feed x). The axes the page offers are exactly `curves.X_COLUMNS`. A group with one x value is not a curve along that axis and is left out with a note. Pre-v15 rows have no `Figure/Table`: they group by conditions only, and a row that also lies on a ≥3-point sweep along another axis (Swain & Otu's concentration sweep at pH 1.75 shares its 500 mM point with the pH sweep) is drawn on both and named in the hover — never silently assigned to one. A curve with < 3 x values or a repeated x is drawn as points, not a line.
- D = [%E/(100 − %E)] / (O/A) only where `Phase ratio (O/A)` is recorded; reported D wins; computed values are hollow markers / labelled "computed". Where O/A is unknown, slopes use log[%E/(100 − %E)] (= log D + log O/A: same slope) and β uses the %E ratio (O/A is in the set key, so it cancels). `derived.RELIABLE_PCT` (5–95 %E) bounds every log-D fit and β; pH½ and β interpolate only between bracketing measured points, never extrapolate (`calculator/predict.py`'s rule). Initial and equilibrium pH are drawn on separate charts, never one axis.
- Series styling: 8 CVD-checked hues × (circle/solid, square/dashed) = 16 series max (`charts.MAX_SERIES`); an element keeps its style when every series is a different element. Streamlit sizes a chart's total height *including* the bottom legend, so `charts.height` adds legend rows.

### Key invariants (violating these breaks the design)

- **Read/write split is enforced two ways.** Write actions call `auth.require_write_access()` first; read consumers open the DB via `connection.get_readonly_conn()` (SQLite `mode=ro`). The assistant's `query_database` tool has a *second* independent backstop, `assistant/sql_guard.py`, which rejects anything but a single SELECT/CTE over a table whitelist even if the model is jailbroken. When touching the assistant's DB access, keep both layers.
- **Prompt versioning = reproducibility.** The extraction prompt is a pinned, versioned file in `prompts/extraction_vN.md`, loaded only through `extraction/prompt_loader.py`, which records the version + sha256 on every run. Improving extraction means dropping in a new `prompts/` file, adding a `prompts/CHANGELOG.md` entry, and bumping `EXTRACTION_PROMPT_VERSION` — **no pipeline code changes**. A version with a recorded `prompt_runs` row is immutable: never edit it, fork a new version. Never hardcode prompt text elsewhere.
- **Coexistence, not replacement.** Re-extracting a paper under a new prompt version inserts a new `prompt_runs` row; it never overwrites old data. `v_current_best` (defined in `database/schema.sql`) resolves "each paper's most recently *approved* run" at query time, so old and new prompt versions coexist without migration. Consumers must read `v_current_best`. Note it orders by approval time, not by version string — sorting `prompt_version` as TEXT ranks `extraction_v9` above `extraction_v10`. A side effect worth knowing: re-approving an older version makes it current again, which is the only rollback path for a regressed version.
- **The DB is only written on human approval,** through the single atomic transaction in `database/merge.py::commit_extraction`. `extraction/runner.py` produces an `ExtractionResult` and touches nothing persistent except each run's transcript (`data/transcripts/`). The bulk CLI never merges. `review_log` is append-only and records no reviewer identity (single shared password ⇒ actor unknowable).
- **Only openly-licensed papers enter the DB.** `commit_extraction` raises `merge.LicenseRequired` (writing nothing) unless the paper's licence — passed in (from the staged `PaperRef.license`, set from the open-access manifest by PDF sha256 at ingest, or by hand via `staging.set_license`) or already on its `papers` row (`papers_repo.set_license`) — is in `config.OPEN_LICENSES`. Swain & Otu 2011 (Elsevier, merged before the gate existed) was removed from the DB in 2026-11; it could only come back with a recorded open licence. The first merge of each day backs the DB up to `data/backups/master-<date>.db` (`connection.backup_once_a_day`).

### Extraction flow (`extraction/runner.py`)

Shared pre-pass + parse + QA logic (`runner._prepass`, `runner._postprocess`) backs two entry points: `extract_paper()` (synchronous, blocks until done) and `submit_batch()` / `batch_status()` / `collect_batch()` (the Anthropic Message Batches API — 50% cheaper, asynchronous; opt-in via a toggle in `app.py`, default off — except that a paper the upload triage marks raster *always* takes the batch path, first extraction and QA re-extraction alike (`runner.must_use_batch`; `BatchItem`/`BatchRequest` carry `qa_feedback` for that). Reason: a raster paper's code-execution loop runs several times longer than a vector paper's and every iteration re-reads the whole growing transcript, so a raster paper is where the batch discount matters most, and a batch turn runs on Anthropic's side rather than over a streamed connection the laptop has to keep alive (2026-09-22: ~$7.50 synchronous run). Verified live once on 2026-07-29 at ~$2.26/paper with accuracy matching the sync path; re-verify on 1-2 papers after any change to `_message_kwargs`). Both paths describe a paper to the client as an `anthropic_client.BatchRequest` (prompt text, model, pre-pass block) — the runner's `BatchItem` is the superset persisted between submit and collect. Both paths pause a turn at the same server-side-tool-loop cap — **50 code-execution iterations**, measured on Sonnet 5 (sync on 2026-09-25, batch on 2026-09-16 and 09-24; older notes claiming 10 for sync and "higher" for batch were wrong); a batch item that pauses is transparently finished off with a synchronous continuation (`anthropic_client._continue_until_done`, reloading the item's pinned prompt by version, reusing its already-uploaded `file_id`, and resuming in the same code-execution container by passing the paused turn's `container.id` — without it the API starts an empty sandbox and the replayed transcript points at renders and scripts that are gone; an idle container is checkpointed and restorable by id for 30 days) rather than surfaced as an error — only that one item pays sync price for its remaining iterations.

1. Load pinned prompt (`prompt_loader`).
2. **Deterministic curve pre-pass** (`extraction/curve_prepass.py` → `extraction/curve_extractor/`): counts figure markers from the PDF's own vector geometry, purely and with no API call, and injects the counts as a grounding "ground truth" block into the prompt + a QA cross-check anchor. It only marks a page *authoritative* when series counts are internally uniform AND no colour group spatially splits across panels (`_looks_panel_merged` — catches a two-panel figure that inflates every series by the same factor, which uniformity alone passes); multi-panel and raster figures are downgraded to hints. A page of an *overlaid* PDF — its text carries the hidden-draft marker "FOR PEER REVIEW", or a calibrated axis reads two or more tick values twice — is never authoritative and forwards no counts or coordinates, only a note to digitise what the rendered page shows (MDPI drafts hide an earlier layout under the final page; on the 2026-11 trial that doubled the counts and garbled the coordinates of two "authoritative" pages). On a raster page it lists **every** figure-sized embedded image (`RasterFigure`: PDF bbox + native pixel size, one per image, not per page — Quinn et al. 2015 prints two figures on pages 2 and 4; images under 100 pt a side are logos and skipped). A failure here degrades to "no anchor" and must never block extraction. As of `extraction_v8`, authoritative pages also carry the pre-calibrated (x, y) marker coordinates the vector path already computes (`curve_extractor.extractor` runs axis calibration per page) as a `DIGITIZED CURVE DATA` JSON block, so the model can skip its own calibration/clustering for those (vector, filled-marker) series entirely — scoped to the same authoritative-page trust gate; monochrome/stroked series and estimate/raster pages are unaffected and still get full visual digitization. This hand-off first fired on a real paper on 2026-09-29, once `detect.find_plot_frame` took the stroked plot border instead of the figure's filled background and `calibrate.auto_ticks` joined labels the PDF stores one character per text run (Swain & Otu Fig. 2: 171 points, median error 0.01 %E vs the approved data).
3. Anthropic API call (`extraction/anthropic_client.py`) → parse (`extraction/parse_output.py`). The client uploads the PDF once via the Files API and hands it to the model **two ways in one turn**: a `document` block (visual reading of legends/markers) and a `container_upload` for the **code-execution tool**, where the model renders pages with PyMuPDF and digitizes them. A second `container_upload` carries the **sandbox toolkit** (`extraction/sandbox_toolkit.py`): the repo's own `curve_extractor` package zipped, plus a per-run "SANDBOX TOOLKIT" user-turn block (injected like the pre-pass block, never part of the pinned prompt) that tells the model how to load it, what the sandbox has installed, and which functions replace hand-written raster digitizers. Since 2026-09-29 the workflow for a scanned figure is the sibling ree-extraction-local project's, ported into `curve_extractor`: `raster.find_panels` (every panel of a whole figure) → `legend.find_swatches` + `legend.match_markers` (markers found by template-matching the figure's own legend swatches, so they come back grouped by series) → `legend.label_centres` + `calibrate.fit_ticks` (tick-label positions paired with the values the model reads) → `fits.reassign` / `fits.drop_off_line` (log D series are straight lines); `raster.detect_markers_in_image` remains for figures whose legend has no drawn swatches. On Quinn Fig. 1 (Nd panel) this reproduces the local pipeline's 18 of 22 hand-checked markers with no false positives, and it runs under the sandbox's library versions (checked in a Python 3.11 / PyMuPDF 1.21 / scikit-image 0.23 replica). It exists because loop length is the cost driver — every code-execution iteration re-reads the whole growing transcript — and on a raster paper the model was spending most of its loop probing the sandbox and re-implementing that code. The toolkit's file id is persisted on a `BatchJob` so a paused item's continuation rebuilds the request exactly as sent (a job from before the toolkit rebuilds without it). The guide and the user-turn instruction (`anthropic_client._USER_INSTRUCTION`) state the sandbox facts the model otherwise spends iterations discovering: the PDF is `$INPUT_DIR/paper.pdf`; rendering goes through the toolkit's `pages.render`, which uses whichever of pypdfium2 / PyMuPDF / pdfplumber is installed (the sandbox's PDF libraries changed under this pipeline — PyMuPDF worked and pdfplumber did not on 2026-09-25, the reverse on 2026-10-07 — so no instruction names a renderer); pdfplumber reads vector objects and text; there is no internet, so nothing can be installed; printed output must be summaries (a printed list of legend swatches once dumped 1.3 MB of arrays into the transcript); and **the model never sees images it renders in the sandbox** — it reads figures from the `document` block only, and opening a PNG with the file viewer returns base64 that every later iteration re-reads. Keep those texts true when the sandbox changes. `curve_extractor` keeps `pdfplumber` and `scikit-image` as lazy imports: everything that takes a page or an image must load without them (pdfplumber was broken in the sandbox until 2026-10; scikit-image is present there but stays optional). Both the synchronous and Batch API paths build their request from the same `_message_kwargs()`, which sets: adaptive thinking; **two prompt-cache breakpoints** — one on the system prompt (1h TTL) and one on the last user-turn block after the PDF (5min TTL), so the PDF is reused rather than rebilled across the model's internal code-execution tool-loop iterations; and a `task_budget` (`output_config`, beta `task-budgets-2026-03-13`) as a self-moderated backstop on total spend. Token usage (`input_tokens`, `output_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`) comes back on `ExtractResponse`/`ExtractionResult` and is persisted on `prompt_runs` — a high `cache_read_input_tokens` share confirms the cache breakpoint is working. (Context editing, `clear_tool_uses_20250919`, was tried and reverted here — clearing mid-conversation breaks the prompt-cache prefix for everything downstream of the clear, so it forces cache-*write*-priced tokens where this pipeline was previously getting cache-*read*-priced tokens; it measured as a 2-3x cost regression on a live run, not a saving.)
4. **QA checks** (`validation/checks.py`): pure, unit-tested functions producing a `QAReport` of RED (merge-gated) / AMBER (warning) flags. Curve-shape checks work per *curve* as `validation/curves.py` defines it (shared with the Analysis page): within one `Figure/Table`, x is the numeric condition along which the rows form the longest curves (`figure_x`; a contact-time grid is kinetics; a figure where nothing numeric varies within a series — one bar per extractant — has no x), and a curve is the element + every other condition column. Before 2026-11 the key lacked `mixing method`, `Material Process`, `Sources`, `Acid Solution`, `Diluent` and every check assumed x = pH, which made about two thirds of the trial's AMBERs false. The checks: **row_count_sanity** (RED: a figure's curve with only 2 points along its x — the stopped-at-the-text-endpoints failure; there is no absolute "too few" beyond that, real series have 4–7 markers as often as 10–20), **sparse_sibling** (AMBER: a series with under half the points of the fullest series of its figure — Ce 1 of 5), **repeated_x** (RED: rows of one curve with every recorded condition equal and clearly different values — the varied axis was lost, e.g. a wt% sweep), **treatment_y_column** (RED: `Stripping`/`Scrubbing` rows with `Extract%`, or extraction rows with only `Recovery %`), axis bounds, **monotonicity** (AMBER: a zig-zag along the curve's own x — two or more changes of direction; one maximum is chemistry), **off_curve** (AMBER: points far off the log D line — only on pH curves that are not `initial` pH and do not level off inside the 1–97 % band), **sampled-from-line** (RED: a series evenly spaced in pH *and* on one log D line within 0.01 decades was generated from a fitted line, not digitised — caught all 17 series of the fabricated extraction_v10 Quinn result with no false positive on any real extraction on disk), **arithmetic** (RED: RRE mM ≠ ppm ÷ atomic mass, or molar ratio ≠ extractant mM ÷ element mM, on the same row; and %E vs **D at the row's phase ratio**, `%E = 100·D/(D + A/O)`, on extraction rows only), **separation_factor** (AMBER, narrow on purpose: an SF that matches its pair's own β = D_a/D_b only with the two elements exchanged, against the direction the figure's other points or a stated `SF Dy/Nd` in `Material Process` set — a swapped pair; an SF fitting neither direction is not flagged, since on the trial that was the paper's own inconsistency), **feed_total** (AMBER: one RRE mM shared by 3+ elements with no ppm — a total copied onto every element, as extraction_v10 did on Quinn), duplicates (same-curve repeats only), vocabulary drift (a stated speed or detail after the name is ignored: "stirring, 450 rpm" is "stirring"), `pH type` vocabulary, element scope (rare earths only; element groups such as LREE get no rows), **provenance** (AMBER: rows with no `Figure/Table`), cross-checks against the paper's stated `text_endpoints` on any x column (`x_basis` must be the schema column name — an unknown basis, or an `x_value` equal to the y, is an AMBER rather than a silent skip; a mismatch is RED only when the statement can be pinned to one curve of the element, else AMBER) and against the deterministic marker counts.

The review UI (`app.py`) is UI only; everything that must outlive a Streamlit server restart goes through `extraction/staging.py`: each extracted table is staged as a flat `data/staging/<sha>.meta.json` sidecar that holds the table itself (the commit point) plus a `<sha>.xlsx` copy for opening by hand (`staging.stage` / `load_all` / `discard`, round-tripping `ExtractionResult` field-by-field so older sidecars — 26-column tables in the .xlsx, provenance as `row_figures` — still load). Every staging write is temp file + `os.replace`; a re-extraction moves the result it replaces to `staging/_superseded/`. A QA-flagged paper gets a third review action besides approve/reject: "Re-extract with QA feedback" re-runs the extraction with the previous attempt's flags injected as a user-turn block (`runner.qa_feedback_block` → `extract(qa_feedback=...)`, or a one-paper batch job with `qa_feedback` on its `BatchItem` for a raster paper), replacing the staged result — on-demand only, never automatic. A submitted-but-not-yet-collected Batch API job is a `staging.BatchJob` with its own sidecar (`_batch_<id>.batch.json`) so it survives a restart too — check status from the "Batch API jobs" section (or `python -m extraction.bulk collect`) to fold results into the normal staging queue once the batch ends. Submit / reconcile / collect / discard live in `extraction/batch_jobs.py`, shared by the dashboard and the bulk CLI: a submission is journaled as a `_pending_<job>.batch.json` before its first upload and marked just before the (never-retried) create call, so a crash can't leave an untracked paid batch or orphaned upload — `batch_jobs.reconcile` (the CLI's `status`) adopts the batch it created or deletes its uploads. Submission refuses any paper staged, in any job, or in a running sync extraction (`staging.in_flight_shas`). Collection holds an OS `flock` (`staging.collection_lock`; released by the OS when the process dies — no staleness window), saves every batch result and every continuation turn to `data/transcripts/<batch_id>/<sha>.json.gz` (`extraction/transcripts.py`, `model_dump(exclude_unset)` ↔ `BetaMessage.model_validate`, which round-trips the exact request body, so the append-only transcript rule holds) before working on it, resumes a paused item's continuation from its last saved turn, and drops each paper from the job as it is staged — re-running it re-pays nothing. An exhausted credit balance (`anthropic_client.is_credit_exhausted`: 402 `billing_error` or "credit balance") stops further continuations in that collection and leaves the failed papers on the job, resumable. An extraction that fails after the model call has started raises `anthropic_client.ExtractionFailed`, which carries the tokens billed up to the failure (completed turns plus a dying stream's partial message, or the finished call behind a parse/QA error); the page appends every such failure to `data/staging/_failed_runs.jsonl` (`staging.record_failed_run`, with the run's transcript path and whether credit ran out) and lists them in a "Failed runs" expander. The raw output of every paid run — success or failure, sync or batch — is in its transcript under `data/transcripts/`.

### Layout notes

- `data/` (gitignored): `incoming/<sha256>.pdf` source PDFs, `staging/` pending review, `transcripts/` every paid turn per run, `backups/` daily DB copies, `open_access/` the licensed-paper manifest + PDFs (owned by another agent), `exports/` approved per-paper CSVs named `<Short_citation>_<n_rows>.csv` (e.g. `Swain_&_Otu_322.csv`, via `database/naming.py::export_filename` — the same helper computes the `Output file` column of the Database page's Tracking sheet tab, which mirrors the external "REE Paper Tracking" spreadsheet's 14-column layout), `master.db`.
- Hosted viewer: `viewer.py` is a second entry point (`st.navigation` over `pages/1_Database.py` and `pages/4_Analysis.py` only) that defaults `DB_PATH` to `viewer_data/master.db`, the trimmed copy `database/snapshot.py` writes (raw model output and local PDF directories removed). This repository is public, so `viewer_data/` is gitignored; `publish_viewer.sh` copies HEAD plus the snapshot into a separate checkout of the private hosting repo (`NicholasHat/ree-viewer`, refusing if that repo is not private) and pushes it. Never commit the snapshot here.
- `database/`: `connection.py` (rw + ro conns, applies schema), `*_repo.py` (per-table CRUD), `merge.py` (the one write path), `browse.py` (read views for the DB page). Schema lives in `database/schema.sql` (idempotent `CREATE ... IF NOT EXISTS`, applied on startup) — `migrations/` mirrors changes for the record but nothing executes those files directly — add a numbered file for every `schema.sql` change (nothing enforces this, so it drifts silently; 0005 was backfilled). Because SQLite's `ALTER TABLE` has no `ADD COLUMN IF NOT EXISTS`, a column added to an existing table (e.g. `prompt_runs`'s usage columns, `papers`'s tracking-sheet columns) needs a matching entry in `connection.py`'s per-table column dicts (applied by `_ensure_added_columns` at startup), not just a `schema.sql` edit, or pre-existing DBs never pick it up. Views listed in `connection._VIEWS` are dropped and recreated on startup, so editing a view's definition in `schema.sql` alone *is* enough — add any new view to that tuple.
- The 35 extraction columns have exact human-readable names *with units and punctuation* (e.g. `"Rare Earth Elements (REY:La, Ce, Nd)"`, `"Extractant Conc. (mM)"`, `"Phase ratio (O/A)"`); they are the DataFrame columns, the SQLite columns, and the XLSX headers. `validation/schema.py` is the single source of truth — `LAB_COLUMNS` (the lab spreadsheet's 26, never renamed or reordered) + `ADDED_COLUMNS` (Diluent, Co-extractant, Co-extractant Conc. (mM), Phase ratio (O/A), Contact time (minute), Distribution ratio (D), Total REE feed (mM), pH type, Figure/Table) — coerce/validate through it rather than re-listing columns (`database/connection.py` derives its added-column dict from it; `tests/test_schema_contract.py` checks schema.sql and the assistant prompt against it). On a pre-2026-11 DB the added columns sit after `merged_at`: read columns by name. `Phase ratio (O/A)` for a solid sorbent is m/V in g/mL so `%E = 100·D/(D + 1/OA)` holds for both systems; `Leaching time` is only for a leaching step (contact time moved to `Contact time` in v15). The *wire format* the model returns them in is separate and versioned in the prompt: `extraction_v7`+ uses a compact positional `{"columns": [...], "rows": [[...], ...]}` shape rather than v5.1–v6's one-object-per-row shape; `columns` may be the 26 lab columns (v7–v14; added columns load null) or all 35 (v15+; v16 keeps v15's output shape); `extraction/parse_output.py` accepts all of these. `extraction_v13`+ also returns `figures` (every figure, digitised or why not), summarised with each row's `Figure/Table` by `extraction/provenance.py`; v13–v14 gave row sources as a parallel `row_figures` list, folded into `Figure/Table` when it lines up (it didn't on the trial's three longest tables).
- `evaluation/` (offline, read-only, no API): `match` pairs two extraction tables of one paper row by row (same element + spelling-normalised extractant; pH within ~0.15, extractant concentration within ~12 %) — ported from ree-extraction-local's scorer; `sources` loads this pipeline's result for a PDF by content sha256 (staged, else `v_current_best`, else failed runs' cost only — re-collections of one batch counted once, which is why `record_failed_run` takes `batch_id`) and the local pipeline's by file stem; `cost` prices recorded usage (`ExtractionResult.via_batch` halves it); `compare` is the CLI writing `summary.csv`, per-paper JSON, `report.md` and `excel/<paper>.xlsx` (the two pipelines' rows side by side with each row's source figure, plus both full tables — for checking against the paper by hand) to `data/comparisons/<date>/` (gitignored: it holds rows from licensed papers). With no reference, agreement between the two independent pipelines is the signal; `--ref-dir` adds recall/precision against `<stem>.csv` references.
